    Migrate while the third pin serves

    0013_matte_jobs widens the three lane checks on media_job_lanes, queue_lane_events and worker_lane_grants, and the kind, lane and board/story checks on media_jobs. It seeds the matte FIFO and adds matte_releases SMALLINT NOT NULL DEFAULT 0 with column-scoped runtime UPDATE permission. The constraint changes and writes commit together. The migration locks grants, media lanes, pause events and media jobs in that order. PostgreSQL's 500 ms timeout applies per lock acquisition. The grant lock can queue and the other three prelocks use NOWAIT. A readiness or worker-authentication read queued behind the migration can wait for the grant lock budget plus DDL and commit, about 10 ms at the installed table sizes. The independent fixture measured a 502 ms grant read when the holder released just before timeout. The guarantee covers lock acquisition. API readiness and worker requests can take longer. A lock timeout rolls the upgrade back to 0012_release_constraints and the Job retries within its two-retry, 300-second budget. Keep sampling the old pods while the Job runs. Record when the active window is too short to sample.

    Source verified. The 80975a9 readiness probe selects existing columns and tables with LIMIT 0. It doesn't require an exact Alembic revision. Old claims and pause reads use explicit run, voice and image lanes. Old media inserts and updates use named columns, and the release counter's server default covers old inserts. The widened predicates still admit the original job kinds and their original board/story associations. Old catalog, release and archive queries use the same columns and rows. The compatibility is for the original workloads. The old job provenance parser cannot display a matte job document, and the matte lane is absent from its queue controls. Retain those records for a forward recovery. Old readiness · Old queue SQL · Old job parser

    Flux owns the migration and registration Jobs. The studio apply stage depends on the migration Kustomization and its successful digest-named Job. The rollout keeps maxUnavailable: 0 on the API.

    The migration Job verifies the TLS login before upgrading and reports its committed head. Each migration and registration read identifies the current Job UID, requires exactly one succeeded pod owned by that Job and reads the last line starting with { from its successful container. For a registration the last JSON result identifies the worker and the earlier matching audit line confirms its status. An older failed pod is normal after a retry. A Complete Job with zero or multiple succeeded pods fails the audit.
