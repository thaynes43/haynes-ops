## One-bounce source proof and recommendation

The unmodified combination is NOT order-safe: stable-name dev-env-scripts ConfigMap can update before helm-controller changes image. Reloader sees new data and can roll the old image, followed by a second image rollout. Kustomize and Helm are separate controllers; a single Git commit provides no atomic ordering between them.

Rendered using exact app-template5.3.0 (`sha256:0e13b145656490310ada364d8eb708e5f4f6384c7deb60d3f5f0fa56950ff63a`). Source chart controller annotations render on Deployment.metadata, not Pod template. Canonical JSON template hashes:

Prep/restore metadata alone produces zero intended Deployment rollout. If choosing this plan, driver must observe prep reconciled with auto=false before activating, keep false through CM processing/new pod readiness, then restore only after the relevant Reloader update has been processed; a queued CM event processed after restore is an avoidable second-roll risk.

**Simpler and stronger source method:** in the same activation change as requirements/image, annotate ONLY generated dev-env-scripts ConfigMap with `reloader.stakater.com/ignore: "true"` via that generator's `options.annotations`. Atomic ConfigMap API update includes both data and annotation. [Pinned Reloaderv1.4.22 ShouldReload](https://github.com/stakater/Reloader/blob/v1.4.22/pkg/common/common.go) checks changed-resource ignore before workload opt-ins; [config.go](https://github.com/stakater/Reloader/blob/v1.4.22/pkg/common/config.go) uses that event object's annotations. Thus that exact update cannot trigger Reloader, even if processed later. Image change triggers the one intended V1 Deployment replacement. After driver verifies new image/config and readiness, remove only the ignore annotation in a cleanup commit: [data hash function](https://github.com/stakater/Reloader/blob/v1.4.22/internal/pkg/util/util.go) excludes metadata and [update handler](https://github.com/stakater/Reloader/blob/v1.4.22/internal/pkg/handler/update.go) skips identical data hashes, so cleanup causes no Reloader rollout. Other ConfigMaps/Secrets remain opted in throughout. [Official behavior documentation](https://github.com/stakater/Reloader#-resource-level-ignore-annotation).

Kustomize overlay proof confirms same named ConfigMap, exact new requirements SHA2561473db2b50685a7042538dcfba3d1a8c21e908d3e499c4f14fd19ed69c3c544d and ignore=true; metadata removal leaves identical Reloader data-hash input and unchanged Helm values/template. ## Claims and shutdown: exact pinned archive limits

No supported no-auth CLI command enumerates active My Machines claims in this pin. Worker subcommands are start/controller/debug plus hidden self-test. Debug authenticates and calls account/worker visibility APIs; its JSON has identity/auth/routing/visibility probes, not current active claims. It may output account identifiers. Do not run it as an idle check. Optional management /readyz and hidden worker-api WatchStatus expose connected/claimed state only if those listeners were enabled at launch; current supervisor enables neither, so do not add/restart them merely for this check.

Static archive files retained under `/tmp/v1-cursor-static/`:2721 contains worker mode/SIGTERM management;3548 contains bridge claim lifecycle;6174 contains debug;index contains command registration. Operational claim acquisition logs include a successful-claim INFO message (already sent verbatim to driver); release-by-bridge exits, claim mismatch exits and renewal exits have distinct WARN messages. Store-controller detach is weaker evidence and must not be equated with no active worker claim. Lifecycle resetInstance invokes completed session hooks, ends claim, clears claimedBcId and sets claimed=false, but contains no dedicated INFO idle/completed log marker. Therefore claim with no terminal marker is uncertain; absence in rotated/incomplete logs is not proof of no claims. IDs/content need not be printed to count/classify markers locally. Preserve current work before restart as driver is doing.

SIGTERM maps to USER_SIGNAL and immediately enters worker shutdown. Bridge stop marks permanent stop, sends best-effort goodbye (1s bound), aborts stream, cancels active RPCs, waits at most5s for claim lifecycle critical sections, then ends remaining session hooks as aborted and tears down stores/listeners. It does NOT wait for the claimed cloud task to complete. Permanent-store close is best effort with flush:false, so filesystem/WIP preservation and any application-specific durable work must already be complete. Supervisor forwards TERM to its child and waits; source fixture verified forwarding. A restart is not a safe job-drain mechanism and daemon liveness is not claim acceptance evidence.
