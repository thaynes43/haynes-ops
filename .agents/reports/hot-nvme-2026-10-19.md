Verdict: FALSE ALARM from a monitoring change. No thermal problem. No urgent physical action.

## What fires
- Alert `SmartDeviceHighTemperature` (severity critical, receiver `pushover`), host `haynestower` (Unraid NAS), job `smartctl-exporter-haynestower`.
- 8 alerts: nvme0..nvme3 x `temperature_type` in {`op_limit_max`, `critical_limit_max`}. Fingerprints: 0dd011457a39a3f6, 58af56ce7f7c0ba0 (nvme0), 5d24ebc01befda4d, e4bb97bf6170cc8f (nvme1), 3e3d87809bb2f542, 8832930e89ffa120 (nvme2), 20c913862f9d5c77, bb1a24c1b350fa39 (nvme3).
- Current firing episode startsAt 2026-10-19 11:09:45 EDT. No silences active.

## Why (rule bug exposed by an exporter change)
- Rule: `kubernetes/main/apps/observability/smartctl-exporter/app/prometheusrule.yaml`: `expr: smartctl_device_temperature > 65`, `for: 15m`. Unchanged since 2026-07-10 (applied by kustomize-controller). No git change to rule/scrapeconfig/route near onset.
- The rule has no `temperature_type="current"` filter. The NAS exporter (owner-installed docker container `smartctl-Exporter`, image `prometheuscommunity/smartctl-exporter:latest`, outside git) was recreated 2026-10-12 03:31 EDT (Unraid auto-pull of `:latest`; image ~13 days old). From the first scrape after that (03:35 EDT) it emits two extra series per NVMe: `op_limit_max`=85 and `critical_limit_max`=95. These are the drive's Warning/Critical Composite Temp thresholds (smartctl: 85 C / 95 C; nvme id-ctrl wctemp 358K, cctemp 368K), not temperatures. 85 and 95 are > 65, so the rule fires: pending 03:35, firing from ~03:50 EDT on 2026-10-12.
- Before 2026-10-12 03:35 EDT no limit series existed (count 0), so the rule never fired.
- Real temps (`temperature_type="current"`): nvme0..3 = 34/35/38/34 C now; 7-day max 42/42/44/42 C. HDDs on the same box 31-47 C. Warning/critical composite temperature time = 0 on all four drives. Far below 85/95 C.

## Why "new and repeated" notifications
- Route: `severity=critical` -> `pushover`, group_by [alertname, job], group_wait 1m, group_interval 10m, repeat_interval 12h. So Pushover re-sends at least every 12h while firing, plus on any membership change.
- Exporter scrape drops the limit series for one 60 s sample occasionally (the series vanish while `up` stays 1). Prometheus has no `keep_firing_for`, so the alert resolves immediately, re-enters pending, and re-fires 15 min later: a RESOLVED then a new FIRING Pushover each time. Dropouts (EDT): 10-12 11:43, 10-13 16:07, 10-15 00:00, 10-16 00:01, 01:47, 06:00, 23:15, 10-17 15:06, 10-19 10:53. The 10-19 10:53 dropout produced today's resolve + re-fire (11:09:45).
- The exporter container was also restarted 2026-10-19 03:18 EDT (docker StartedAt 07:18:26Z; cause not determined).

## Classification
(b) monitoring change: an unfiltered rule meets new exporter series. Not (a): no real thermal rise.

## Recommended fix (needs a PR; not done here)
Change the rule to `smartctl_device_temperature{temperature_type="current"} > 65`, (the limit series then no longer matter, so the dropouts stop causing flaps). Optionally pin the NAS exporter image off `:latest` (outside git). Fix PR is user-visible alerting behavior: coordinator decision.

Safe: current temp <= 44 C, critical warning bits are only the known 0x04 on nvme1/2, and real `temperature_type="current"` over-temp alerts, SmartDeviceCriticalWarning, MediaErrors, TestFailed stay active. Silence only the limit-series flavour for 72 h (until the rule PR lands):
