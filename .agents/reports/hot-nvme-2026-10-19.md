## Why (rule bug exposed by an exporter change)
- Rule: `kubernetes/main/apps/observability/smartctl-exporter/app/prometheusrule.yaml`: `expr: smartctl_device_temperature > 65`, `for: 15m`. Git shows this rule unchanged since it was added in commit d21ae3ea (2026-07-13, PR #2032) until the proposal in draft PR #4102; no git change to rule/scrapeconfig/route near onset.
- The rule has no `temperature_type="current"` filter. The NAS exporter (owner-installed docker container `smartctl-Exporter`, image `prometheuscommunity/smartctl-exporter:latest`, outside git) was recreated 2026-10-12 03:31 EDT (observed: container start time). What triggered the recreation (e.g. an Unraid auto-update or a manual action) was NOT verified, and no image version or digest was observed, only the `:latest` tag. From the first scrape after that (03:35 EDT) it emits two extra series per NVMe: `op_limit_max`=85 and `critical_limit_max`=95. These are the drive's Warning/Critical Composite Temp thresholds (smartctl: 85 C / 95 C; nvme id-ctrl wctemp 358K, cctemp 368K), not temperatures. 85 and 95 are > 65, so the rule fires: pending 03:35, firing from ~03:50 EDT on 2026-10-12.
- Before 2026-10-12 03:35 EDT no limit series existed (count 0), so the rule never fired.
- Real temps (`temperature_type="current"`): nvme0..3 = 34/35/38/34 C per the investigator's reading; the coordinator re-queried Prometheus at 11:19 EDT and saw 35/35/37/35 C. 7-day max 42/42/44/42 C (investigator-reported, not re-checked). HDDs on the same box 31-47 C. Warning/critical composite temperature time = 0 on all four drives. Far below 85/95 C.

## Why "new and repeated" notifications
- Route: `severity=critical` -> `pushover`, group_by [alertname, job], group_wait 1m, group_interval 10m, repeat_interval 12h. So Pushover re-sends at least every 12h while firing, plus on any membership change.
- Exporter scrape drops the limit series for one 60 s sample occasionally (the series vanish while `up` stays 1). Prometheus has no `keep_firing_for`, so the alert resolves immediately, re-enters pending, and re-fires 15 min later: a RESOLVED then a new FIRING Pushover each time. Dropouts (EDT): 10-12 11:43, 10-13 16:07, 10-15 00:00, 10-16 00:01, 01:47, 06:00, 23:15, 10-17 15:06, 10-19 10:53. The 10-19 10:53 dropout produced today's resolve + re-fire (11:09:45).
- The exporter container was also restarted 2026-10-19 03:18 EDT (docker StartedAt 07:18:26Z; cause not determined).

## Classification
(b) monitoring change: an unfiltered rule meets new exporter series. Not (a): no real thermal rise.

## Recommended fix (proposal only: draft PR #4102, NOT merged, NOT deployed)
Change the rule to `smartctl_device_temperature{temperature_type="current"} > 65` (the limit series then no longer matter, so the dropouts stop causing flaps). Optionally pin the NAS exporter image off `:latest` (outside git). Draft PR #4102 holds the change as a reviewable proposal. The live rule is still the old expression. Merge and deploy need Tom's explicit, verified go-ahead.
