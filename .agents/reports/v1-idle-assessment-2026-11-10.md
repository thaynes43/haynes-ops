## 2. Everything else v1 does on its own

**Sidecars, both `while true` loops in the same pod.**

- `gh-refresher` (`helmrelease.yaml:226-230`) runs `gh-token-refresh.sh`. Every 40 minutes (`sleep 2400`, `gh-token-refresh.sh:9-17`) it mints a haynes-dev-bot installation token into the memory emptyDir `/creds/gh_token`. The app container's git helper and `gh` wrapper read that file (`dev-init.sh:193-194` and `:247-271`). The PEM stays in this container's env. v1 `git` and `gh` go dark about an hour after this sidecar stops.
- `auth-watch` (`helmrelease.yaml:258-262`) runs `auth-check.sh`. After 60 seconds, then about daily (`auth-check.sh:17` and `:66`), it probes Claude (env token and the PVC login), `login-check.sh` for the Max login expiry, `codex login status`, and the age of `/creds/gh_token`. A failure pages Pushover (`auth-check.sh:8-15`, `:61-65`).

**Once per boot, not a loop.** `dev-init.sh` links GitOps config into `$HOME`, re-asserts the Claude model, renders Codex config, installs the pinned Codex standalone and `kubectl-cnpg` when missing, sets the git identity and credential helper, seeds Playwright browsers, and writes the `gh` wrapper and the hw-ssh key file when the env var is present. No cron. No second timer.

**Started by `post-ready.sh` besides the five names.** Section 7 (`post-ready.sh:219-274`) starts one Claude standby: `agent-run --repo haynes-ops --agent claude --interactive`. The tmux name is `task-<new id>`, not one of the five. It is skipped when a live `task-haynes-ops-*` remote-control pane is already there (`:228-233`). The circuit breaker (`:141-146`) skips the standby, Codex, the sweeper and the Cursor block together when this script has reached the launch point 3 times in 30 minutes.

## 4. Before replicas can go to zero, and what can stop now

**Has to be true first, in this order.**

1. Tom has this list. OP538 says nothing in v1 is stopped until he has seen it. This file is that list. Merging the held draft restarts the pod; it does not scale it to zero.
2. The work that still lives only on the v1 volume has a copy Tom accepts. The coordinator's OP538 note says four worktrees had commits on no remote, seven had modified tracked files, and all ten `grok-*` worktrees had untracked files. Those copies are in the coordinator pod, not on GitHub. The five `task-*` sessions need an owner's word each, as that note already says. A restart ends those processes. The files stay on `dev-env-home`.
3. Plan 05's drain, which has not been run. The 2026-10-21 cutover did not happen: the pod has been up since 2026-10-23. Each wanted session pushes `agent/*` and writes a handoff; no wanted worktree is left unpushed; orders and memory are copied to `~/.shared/v1-home/` and checked; protected material stays on the volume (`05-cutover.md:78-99`, `:145-163`).
4. Tom's written approval. The date does not approve it.
5. Only then, from a shell in the pod: `agent-run codex-remote stop` (`05-cutover.md:111-114`). Then a separate held draft sets replicas to 0. Do not delete PVC `dev-env-home`. Its StorageClass reclaim is Delete, and the PVC is marked prune disabled (`app/pvc.yaml:19-22`, `05-cutover.md:100-105`).
6. Deleting the app is later than scale-to-zero. Before that, move ClusterRole `dev-env-operator` and drop `dev-env-ops`'s `dependsOn`, keep the 0.6.8 image for `dev-env-ops` and vexa until those move, and remove `dev/dev-env` from the operator's client list and canary client. The cutover plan lists the rest (`05-cutover.md:117-139`).

**Can be switched off now without taking away something someone is using.**

The two Cursor My Machines autostarts. No script, Service, Ingress or CronJob attaches to `cursor-worker-v1` or `cursor-worker-dev-env`. `dev-activity-check.sh` prints whatever tmux names exist; it does not require these two. Decision 79 already says they are not moved to v2. The coordinator's 13:02Z read said both had been idle about 7 days. v2 cursor task pods are how Cursor work runs now. This PR is that switch: `post-ready.sh` writes both disabled markers (`:157-159`) and `cursor-worker.sh up` returns before creating a tmux session while a marker exists (`cursor-worker.sh:104-107`). The running workers keep going until the pod restarts. `main`, `codex-remote`, `wt-sweep`, the Claude standby, both sidecars, the logins and code-server are unchanged.

Do not switch those off yet. `codex-remote` is still Tom's v1 ChatGPT computer. `wt-sweep` is still the disk reaper. `gh-refresher` is still v1's only GitHub token. `auth-watch` is still the pager for v1's own logins. `main` is the tmux server the others use. The standby is still v1's phone Claude session.
