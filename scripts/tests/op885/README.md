# OP885 talosm03 kernel stall and offline detection

On 2026-11-17, talosm03 reported a Linux file-reference warning in `upsmon` on CPU 7 and a sustained RCU stall in a kubelet thread on CPU 8. Ceph client I/O on the node lost progress while Kubernetes continued to report Ready. Home Assistant and ComfyUI timed out. The file-reference lifetime path is the strongest lead. The record does not identify the original invalid reference, the relationship between the two stacks, or the underlying trigger.

This directory contains an offline Loki rule and a PromQL query for checking RBD progress. Both use observed labels for talosm03. OP884 records an accepted restoration. Installation and acceptance for OP885 remain open. Rollout requires Tom's separate approval. Source base `7e9ad5cca5a3325cd2e7b3cf0170a94f034079ea`.

The observed outage mechanism was loss of Ceph volume progress on a partially responsive node. The kernel reported a persistent RCU stall and the local CephFS client reported an MDS hang. The block devices accumulated requests and stopped completing them for sustained periods. The apps that depended on those devices timed out, while the API still reported Ready and Ceph continued serving other nodes. The ordering and the return of I/O after reboot support this mechanism. The record leaves the initiating fault and its exact kernel-to-storage chain unresolved. [OP884 history](https://work.haynesnetwork.com/projects/haynes-engineering/work_packages/884)

## Root-cause leads and missing evidence

| Lead | Evidence and what would distinguish it |
| --- | --- |
| Kernel VFS/file lifetime | In the exact upstream baseline, `__pollwait` takes a reference with `get_file()`, and `file_ref_inc` warns if the prior count is negative. `fget_task_next` uses `__fget_files_rcu` to scan a target task's fd table. The two paths provide a plausible lifetime connection. The logs do not identify a common `struct file`, target fd table or owning PID on CPU 8. Matching Talos build symbols and a retained object/task snapshot or vmcore with both stacks would distinguish a shared reference problem from a second failure. None was available in these reads. |
| NUT client activity | `upsmon` was the user-space caller of `select` on a TCP socket. The machine template includes `siderolabs/nut-client`. The retained streams had no matching pre-fault UPS transition / communications records and no NUT-labelled series in the checked four-hour window. An exact extension build and retained UPS server/client events with socket or fd provenance would establish whether a specific NUT activity was involved. |
| Out-of-tree code | The boot had taint `O` and loaded NVIDIA modules marked `(O)`. `W` appeared after the warning. Neither retained stack contains an NVIDIA frame. An exact module build, matching references or frames from an existing dump, or the same signature in a documented event with a different module set would distinguish module involvement. |
| Hardware, firmware or power | The log identifies MS-01/AHWSA with BIOS `AHWSA.1.22`. Bounded retained `MCE`, hardware-error, watchdog and PCIe searches around the event found no corresponding record. Correlated retained RAS/EDAC records, firmware/watchdog resets, or independent UPS/power/switch events would strengthen a platform explanation. The UDP stream is incomplete and cannot exclude a platform fault. |

Talos v1.13.9 names Linux 6.18.44 and packages revision `f541ca434ee63964319bb912e370f0ed407f8a18`. The amd64 config sets `CONFIG_HZ=250`, and the kernel boot string and warning identify `6.18.44-talos`. All nine nodes reported this release and kernel in retained `kube_node_info` at `18:52Z`. ## Detector and retained replay

The Loki rule emits `TalosKernelRCUStall{cluster="main",node="talosm03"}` from a self-detected, remote or expedited `rcu_preempt` stall header in the last five minutes. It evaluates every minute with immediate firing eligibility. Its output identity is one cluster/node pair even when overlapping CPU reports or retries add to the count. A single genuine stall report is actionable and ages out after five minutes of silence. A file-reference warning by itself is outside the alert expression. The alert annotation points to CPU/stack recurrence, RBD progress, and service checks.

- **Kernel log origin.** Talos v1.13.9 exposes kmsg as the `kernel` service log and embeds the kernel event time in the message. Its normal service logger tags `talos-service` and supplies the outer `talos-time`. GitOps sets `hostname` in talosm03's service-log destination `extraTags`. The only Vector service listener is UDP 6051. The Vector remap maps `hostname` to `node`, `talos-service` to `talos_service`, and uses `talos-time` when parseable. The observed stream has `cluster="main",source="talos",log_type="service",node="talosm03",talos_service="kernel",level="info"`. Kernel severity is in the payload, so the selector ignores `level`. The Vector source and older runbook's dedicated UDP 6050 notes describe a separate path. [Talos kmsg storage](https://github.com/siderolabs/talos/blob/v1.13.9/internal/app/machined/pkg/controllers/runtime/kmsg_log_storage.go) · [Talos service logger](https://github.com/siderolabs/talos/blob/v1.13.9/internal/app/machined/pkg/runtime/logging/circular.go) · [Vector remap](../../../kubernetes/main/apps/observability/vector/app/resources/vector.yaml) · [Omni source](../../../kubernetes/main/bootstrap/omni/cluster-template.yaml)
- **Evaluation and coverage.** At `18:52Z`, Loki and Vector were on talosm05, Prometheus and Gatus on talosm02, and kube-state-metrics on talosw03. The existing Loki kernel rule group is scheduled at 60 seconds (`/prometheus/api/v1/rules`). Prometheus is configured for 30-second rule evaluation and 60-second node-exporter, kube-state-metrics and Gatus scrapes, verified by the runtime CR and retained timestamps. The Ceph mgr samples in the incident window were 10 seconds apart. Both candidate queries are evaluated outside talosm03 and require no Ready transition. Seven of nine nodes had at least one retained kernel line in the 24 hours ending at midnight after the incident. The matching signature returned talosm03 only across a seven-day query. Sparse or absent lines can reflect quiet kernels, forwarding loss, or an unavailable collector. [Loki ruler wiring](../../../kubernetes/main/apps/observability/loki/app/helmrelease.yaml) · [Prometheus and node-exporter wiring](../../../kubernetes/main/apps/observability/kube-prometheus-stack/app/helmrelease.yaml)
- **RBD signal.** Node-exporter's Linux diskstats collector supplies `node_disk_io_now` and the two completion counters. The ServiceMonitor copies the exporter pod's node into `kubernetes_node`. The `instance` label is an address and port, and each `device` is local to that node. The query requires three samples of each field in three minutes, positive in-flight requests at every sampled point, both counters unchanged, a shared latest scrape timestamp at most 75 seconds old, and a successful exporter scrape. It matches all labels before reducing to node/device, so complementary fields from different exporters cannot be joined. A reset or observed completion breaks the match. Ready comes independently from `kube_node_status_condition{node="talosm03",condition="Ready",status="true"}`. Its `node` label identifies the monitored node while `kubernetes_node` identifies the exporter pod's node. [Node-exporter diskstats](https://github.com/prometheus/node_exporter/blob/master/collector/diskstats_linux.go)

## Offline verification

Run from the repository root with the release binaries on disk. The test limits each Go process to `DEV_ENV_CPU_LIMIT` (one by default), runs Promtool and Loki serially, and uses temporary files and a loopback-only Loki instance. The verified release versions are Loki 3.6.11 and Prometheus 3.16.0. [Loki release](https://github.com/grafana/loki/releases/tag/v3.6.11) · [Prometheus release](https://github.com/prometheus/prometheus/releases/tag/v3.16.0)

```bash
python3 -I -B scripts/tests/op885/test_detector.py \
  --loki /path/to/loki-linux-amd64 --promtool /path/to/promtool
```

- **Retained replay** uses the original UTC windows and actual data in Grafana. The offline test replays six narrow excerpts with the original Loki spacing, shifted into the local daemon's ingest horizon, and four projected sets of raw 60-second disk samples. The CSV retains UTC scrape timestamps. Promtool replays their spacing relative to the first sample, with the independently verified `up=1` during each slice and fixture exporter identities.
- **Incident-summary-derived evidence** is labelled OP884, OP874 or OP892 in the timeline. It supplies the original power-cycle/acceptance receipts, incident context and otherwise unavailable pve04 observations. No incident-summary estimates are used as telemetry fixtures.
- **Synthetic cases** supply datapoints for missing and stale inputs, slow I/O, alert expiration and duplicate identity. The local Loki ruler is verified to fire exactly one alert on synthetic inputs, without an Alertmanager configured. This is test evidence for rule behavior and scheduling, independent of the historical timing estimates.

The handoff is for review of the early Loki signal and its single-node coverage. Routing and any live trial require approval, and acceptance has its own evidence step. All files here are outside Flux and Loki sidecar include paths. The next evidence that could narrow the RCA is an existing matching dump, prior kernel log tail, or a pve04 console/host record recovered through OP892's own owner.
